# API 高并发优化实施方案（Gemini 执行版）

编写日期：2026-10-01。代码核对基线：`main`，`178ff25030e6525e8bf616989f3ecb2824de119d`。

复核日期：2026-10-01。已根据同一代码基线完成两轮复核，修正入口鉴权保护、事件缓存保留、池关闭锁顺序、后台收信容量、轮询默认值和任务创建恢复契约，并补充物理邮箱串行限制、数据库错误传播、阶段期限和进程退出边界。后续用户确认多个母号共用同一个 Gmail 收件邮箱，实际工作负载补充见第 10.3.1 节。本文是实施任务单，完成状态以当前代码与验证报告为准；实施前检查已有修改，避免重复实现。以下数值是初始保护参数或压测候选值，不是实测容量承诺，也不是行业统一标准。

## 1. 目标与实施边界

目标：在保留现有业务正确性的基础上，让出号、建立取码任务、查询结果的请求等待及上游活跃占用有界，让热路径可取消、可观测；验证是否能稳定承载 **2000 个不同取码任务，每个任务一个长轮询**。缓存先做安全回收与去重，硬容量的未完成范围单独报告。

实施要求：

1. 继续使用 Go/Gin、SQLite WAL、现有 IMAP/HME 客户端和 EventBus。
2. 对外接入文档与客户端示例统一推荐现有 `/api/external/v2/*`，不新增 v3 或另一套出号/取码服务。
3. 已有路径及其明确的兼容责任保持有效，共享同一套资源保护。兼容邮箱查询与 v2 基线任务的语义不同，不强行互相改写。
4. 保留资源归属、Token 轮换校验、基线边界、幂等键、唯一库存分配、CAS 终态、重启恢复等既有保证。
5. 不引入 Redis、消息队列、分布式锁、数据库替换或通用限流框架。优先使用标准库。
6. 不改变与任务无关的前端、移动端、账号资产和清理策略。
7. 不改 `.env` 的现有秘密，不更换 `ICLOUD_HME_MASTER_KEY`，不覆盖或删除 `data`，不撤销其他人的修改。
8. 实施完成并验证后交付修改与报告；本任务不包含自动提交、推送、生产部署或真实 Apple 批量建号。
9. 本方案适用于当前单实例 Compose 主服务。内存准入器的“全局”指一个 Go 进程，不是集群共享限额；当前 Store 还会申请 data 目录排他锁。不能用 Compose scale 多开共享同一目录的实例来代替本轮容量优化，集群架构不在本轮范围。

## 2. 必须区分的四种数量

| 名称 | 含义 | 示例 |
|---|---|---|
| 邮箱/别名数 | 系统有多少个可用邮箱地址 | 2000 个 email |
| 活跃取码任务数 | 数据库里未完成、未过期的取码任务 | 2000 个不同 request_id |
| HTTP 等待者数 | 当前正在长轮询等结果的请求 | 每个任务一个等待者，共 2000 个 |
| 上游活跃操作数 | 当前正在读取 IMAP 或执行 HME 业务的操作 | 同步 5 个母号，或建立 8 个基线 |

`request_id` 是一次取验证码任务的唯一编号；`lease_id` 是已分配邮箱的租约/分配凭据。一个任务可以被查询多次，但正常客户端同一时间只需要保留一个等待请求。

“每个 request_id 最多 8 个等待者”是重复连接保护，不会自动开启 8 个连接，也不能推导出整机能够承载 `2000 × 8 = 16000` 个等待者。

当前代码还有一个独立的 `defaultVerificationBaselineSlots = 8`：这是**同时建立邮件基线的槽位数**，与拟新增的每任务 8 个等待者完全不同。

## 3. 已核对的实现与问题

以下是静态代码核对结果；本轮未重新执行压力测试或访问真实 Apple/IMAP。

| `MailSyncWorker.syncOnce` | 单轮等待所有母号处理完，最多 5 个并发，每个取得槽位后才启动 8 秒预算 | 区分单账号预算与整轮耗时，验证大规模母号分布及后台进展 |
| `Server.Run` | HTTP Shutdown 与服务关闭共用 10 秒等待预算 | 长轮询取消与后台清理预算分开处理 |
| `deploy/nginx.conf`、`deploy/Caddyfile` | 验证码专属规则匹配 `/api/verify/code`，当前 router 未注册该路径 | 修正真实路由匹配；Nginx 已有全局 130 秒超时，不能误报为所有取码必然超时 |

### 3.1 复核结论与实施优先级

原方案的总体方向合理，但以下条目必须使用本修订版，不能按初版直接实施：

| 初版方案缺口 | 影响 | 修订位置 |
|---|---|---|
| 只在 handler/service 内限制在途请求 | 前面的数据库鉴权仍能被突发请求压满，取消或 DB 故障还可能被误报 401 | T2 |
| 缓存满后拒存新事件、每邮箱只留最新 64 条 | 兼容查询可能漏掉尚未消费的验证码，既有顺序被改变 | T7 |
| 增加引用 pin，但未定义与 Close 的锁顺序 | 当前 IMAP Close 持 map 锁等账号锁；新释放逻辑若反向取锁会引入死锁 | T6 |
| 前台/后台只共用一个先到先得的上游名额池 | 前台持续占用可能阻止已接受任务收信；只保留操作槽还不足以保证能借到池条目 | T3/T6 |
| 为统一文档把生产默认 1 秒改成 2 秒 | 未经测量就增加收码等待 | T8 |
| 创建任务响应丢失后仅要求遵守既有恢复契约 | 当前实际上没有完整恢复契约，客户端无法找回原 request_id | T11 |
| 所有参数采用同一个 65536 上界，全部优化同时作为上线门槛 | 资源关系不明确，改动范围过大 | 第 5、12 节 |

鉴权顺序、默认值和 POST 恢复缺口已通过静态调用链确认。缓存丢码、锁反转和后台饥饿是初版拟议改造的风险推导，不是本轮已通过压力测试复现的现存故障。

最小保护闭环优先完成：入口/等待者保护、可取消鉴权和 Store 热路径、上游与池生命周期、后台保留容量、TTL 清理、关闭和必要统计。T5 批量化、T8 SQL 替换或调大同步并发由基准决定；T11 是独立的网络重试契约补齐，推荐交付，但不能与吞吐优化混为一项。EventBus 硬容量暂不实施，不能声称全部缓存已具备硬边界。

### 3.2 深度复核：仍需明确的实施边界

总体架构保留 Go/Gin/SQLite、持久任务、EventBus 通知和真实邮箱串行化是合理的。保护请求数量、提升处理吞吐和缩短收码时延是三个验收目标，不能用一个并发参数代表全部结果。以下补项已写入对应任务：

| 代码事实或方案缺口 | 必须补足的要求 | 位置 |
|---|---|---|
| IMAP `poolKey` 根据收件邮箱、服务器、端口生成；多个母号可共享同一池键 | 单母号数之外统计不同 IMAP 池键；共享邮箱的串行瓶颈不能靠调大 Worker 并发消除 | 第 10.3 节、A25 |
| 支持 Context 取消不等于有服务端 deadline；ReadTimeout 只约束网络读取 | 鉴权、初始 DB 阶段及交付复查有有限预算，并与长轮询等待期限分离 | T2、A27 |
| 只读准入目前仍在 `Store.mu` 内执行三次 COUNT | 只读预检不等待全局业务写锁，最终配额由原子创建事务仲裁 | T4、A27 |
| `syncOnce` 忽略活跃任务列表读取失败；完成任务函数存在忽略 Scan/rows.Err/结果读取失败的路径 | 数据读取失败不能当作零任务或持久化成功；阻止不可靠发布和 checkpoint 推进 | T4/T5、A24 |
| T11 上版把增加字段/索引与任务插入写成同一事务 | DDL 在启动迁移事务内完成；运行时仅提交任务行、键和指纹，不能每次 POST 做迁移 | T11 |
| `Run` 返回停机错误后，`main.go` 调用 log.Fatal，进程会退出并跳过 defer | Run/main 一起协调清理；后台继续清理的保证仅在进程仍存活时成立 | T9、A26 |

其中数据库错误处理及进程退出路径已从代码确认；串行资源关系和期限分离是必须满足的实现约束。实际漏码、饥饿、2000 任务容量和真实上游时延尚未在本轮运行验证，不能写成已复现或已解决。

后台保留容量本身合理，但应使用少量直接状态实现：操作准入在同一短临界区原子检查全局和前台计数，条目引用在现有注册表协调；不增加多层排队器或给每个任务创建收信 Worker。HME 保留策略仅按真实后台调用需求决定。缓存尚无硬容量是需测量的剩余范围，不能以丢弃结果换取表面稳定。

## 4. 目标数据流与接口约束

正常流程：

```text
POST /api/external/v2/allocate
  全局短阶段准入 -> 可取消鉴权与 scope -> 主体短阶段准入
  -> 幂等、授权、原子库存认领
  返回 email、lease_id、operation_id

POST /api/external/v2/verification-requests
  全局短阶段准入 -> 可取消鉴权与 scope -> 主体短阶段准入
  -> lease 归属 -> 可选幂等重放检查 -> 只读任务配额预检
  -> lease 锁 -> 基线槽位 -> IMAP 上游操作保护 -> 基线读取
  -> 原子幂等/任务配额检查和插入
  返回 request_id、baseline_ready、expires_at

外部业务触发发送验证码：必须在 baseline_ready 后

GET /api/external/v2/verification-requests/:request_id?timeout=30
  全局短阶段准入 -> 可取消鉴权 -> 主体短阶段准入 -> 归属/已有终态
  -> 未决任务才获取等待者名额 -> 订阅 -> 数据库复查
  -> 释放短阶段名额后挂起
  -> 后台按母号批量收信 -> 数据库持久化 -> EventBus 唤醒
  -> 复查原请求凭据 -> 返回结果 -> 释放订阅和名额
```

不可破坏的行为：

- 出号重试使用相同幂等键和相同业务参数，返回同一个分配结果；参数不一致仍为 409。
- 普通外部 Token 出号只认领库存。库存耗尽保留 `503 POOL_EMPTY` 和 `Retry-After: 60`，不会因为高并发保护而自动现场建号。
- 同一 lease 只能有一个活跃取码任务。不带创建幂等键的重复 POST 保持 409；只有 T11 中同一主体、同一键、同一有效参数的请求重放原任务，不按 email/lease 自动重放。
- v2 GET 的 `timeout=0` 以及未指定 timeout 当前都是立即查询。兼容邮箱 handler 的 timeout=0 当前会使用默认 30 秒，沿用既有解析行为，不混用这两个契约。
- 长轮询等待窗口结束但任务尚未过期，v2 返回 HTTP 200 与 `status=pending`；不能把“没收到验证码”改成系统错误。
- 已成功任务再次 GET 返回相同持久化结果，不重新消费另一封邮件。
- 长轮询断开只释放本次 HTTP 等待，不删除持久化任务；后台仍然可以完成任务。
- 兼容邮箱查询的既有 `408 VERIFY_TIMEOUT` 保持，所有成功 JSON/纯文本格式保持。

## 5. 配置方案与 2000 任务配置

以下 `ICLOUD_HME_MAX_*` 等参数是**计划新增**，实施前设置不会生效。只通过一条 `环境变量 -> Config/Manager 设置 -> 服务实例` 链路注入，深层业务代码不各自读取环境变量。

| 计划配置名 | 缺省值 | 2000 任务压测候选值 | 作用 |
|---|---:|---:|---|
| `ICLOUD_HME_MAX_ACTIVE_VERIFICATIONS` | 1000 | 2500 | 持久化活跃任务全局配额 |
| `ICLOUD_HME_MAX_ACTIVE_VERIFICATIONS_PER_TOKEN` | 50 | 2500 | 单主体活跃任务配额；覆盖一个业务 Token 处理 2000 任务 |
| `ICLOUD_HME_MAX_VERIFY_WAITERS` | 1024 | 4096 | v2 与兼容邮箱查询合计的等待者上限 |
| `ICLOUD_HME_MAX_VERIFY_WAITERS_PER_TOKEN` | 256 | 2500 | 单主体合计等待者上限 |
| `ICLOUD_HME_MAX_VERIFY_WAITERS_PER_KEY` | 8 | 8 | 一个 request_id 或兼容邮箱键的等待者上限 |
| `ICLOUD_HME_MAX_API_INFLIGHT` | 128 | 128 | 受保护入口短阶段的全局在途上限，包含鉴权查询 |
| `ICLOUD_HME_MAX_API_INFLIGHT_PER_TOKEN` | 64 | 64 | 单主体短请求/短处理阶段在途上限 |
| `ICLOUD_HME_VERIFY_BASELINE_CONCURRENCY` | 8 | 8 | 同时准备基线的槽位数；需数据支持后才增加 |
| `ICLOUD_HME_IMAP_MAX_ACTIVE` | 32 | 32 | IMAP 活跃逻辑操作数，不是邮箱数量 |
| `ICLOUD_HME_HME_MAX_ACTIVE` | 16 | 16 | HME 活跃逻辑操作数，不等同 TCP 连接数 |
| `ICLOUD_HME_MAIL_SYNC_CONCURRENCY` | 5 | 先 5；多母号场景再测 16 | 一轮同时同步的母号数 |
| 已有 `ICLOUD_HME_MAIL_POLL_INTERVAL` | 保留 1s | 先 1s，另测 2s | 同步触发周期，不保证所有账号在一个周期内同步完成 |

说明：

1. 缺省保留现有活跃任务配额，新增等待者保护；它是初始安全配置，不能用它宣称支持单 Token 2000 任务。
2. 候选配置让 2000 个不同任务各一个等待者在配额上可进入，最终能否稳定运行由第 10 节压测决定。
3. 一个 Token 理论上对 2000 个任务各开 8 个等待者时，首先会被单主体 2500 等待者限额挡住；多个 Token 合计仍受全局 4096 限额约束。
4. 不因采用 Go 就把 IMAP/HME 并发直接加到 2000。HTTP 等待主要等待事件，上游收信按真实母号聚合。
5. `*_PER_TOKEN` 在实现里按稳定主体键计数：`principal.Kind + principal.ID`。Token 换密钥不产生新配额；管理员 API Key/会话也不能绕开全局保护，不以原始密钥或空 ID 分桶。
6. 配置运行期先不支持热更新；修改后通过正常重启生效，避免旧/新容量状态混用。
7. 同步保留容量从已有同步并发推导，不增加一组可独立填错的环境变量。IMAP 初始总量 32、同步并发 5 时，前台活跃操作最多 27；同步并发改为 16 时前台最多 16。同一硬总量内允许后台使用余量，前台不借用后台保留部分。池的借用引用也必须满足 T6 的保留要求。

配置接线必须覆盖 `main.go`、`server.Config`、账号 Manager/池的现有装配入口、`.env.example`、`docker-compose.yml`、`API.md`、`README.md`、`docs/remediation/RELEASE.md`。

校验要求：空值使用缺省；显式 0、负数、非法字符串和整数溢出使启动失败，并报告参数名。内部 Config 零值可继续表示缺省。单主体上限不能大于对应全局上限。任务/等待者数量可采用 65536 作为防误填候选上界，单键 64，入口短阶段 1024；这些只是配置校验边界，不是支持容量。上游参数按资源关系校验：IMAP 活跃操作不超过 IMAP 池硬容量，HME 活跃操作不超过 HME 池条目硬容量；同步并发必须小于 IMAP 活跃上限和 IMAP 池容量，留下前台余量；基线并发不超过扣除同步保留后的 IMAP 前台上限。当前缓存 50/200 保持时，不能把上游操作参数校验上界统一放到 65536。通过测试验证派生值和所有关系，报告具体冲突参数。

## 6. 第一阶段：请求与上游资源保护（P0）

### T1. 共享等待者准入器

主要修改：`verification_service.go`、`verify_handler.go`、`server.go`；可新增职责明确的 `internal/server/request_limits.go` 及测试。

实现要求：

1. 一个 Server 持有一个等待者准入器，同时注入 v2 服务与兼容邮箱 handler。
2. 在单个短临界区内检查并更新全局、主体、资源键三个计数；不得用“SubscriberCount 小于 8，再 Subscribe”的分离操作，避免并发超额。
3. v2 资源键为 `vreq:<request_id>`；兼容路径为 `email:<小写去空格邮箱>`。邮箱查询的所有路由别名共享同一个键。
4. 先校验身份、scope、任务/邮箱归属；不存在或无权限返回既有错误，不创建攻击者输入的长期计数条目。
5. 已有数据库终态直接返回，不受等待者耗尽影响。v2 的 `timeout=0` 不占长期等待名额；若需要临时订阅检查缓存，应保留现有缓存完成与数据库复查语义。兼容查询按真实等待窗口计费，不能因为参数写 0 就绕过其默认 30 秒等待的保护。订阅总数可短暂包含受入口短阶段约束的即时订阅，不应与长期等待者计数机械相等。
6. 未决长轮询在建立订阅前获得名额，使用 `defer` 在所有正常、失败、超时、取消路径释放。计数归零删除 key，拒绝请求不遗留条目。
7. 保留订阅后的数据库复查，不能引入“刚查完状态、邮件恰好落库，订阅却漏掉通知”的竞态。
8. 释放后计数不能负数；同一释放函数最多释放一次。计数 map 不按历史 request_id 无限积累。
9. 准入失败直接返回，不等待一个名额、不增加排队 goroutine。

建议错误契约（新增代码统一映射，成功响应不变）：

| 原因 | HTTP | code | Retry-After |
|---|---:|---|---:|
| 单 request_id/email 等待者已满 | 429 | `VERIFY_WAITER_LIMIT` | 1 |
| 单主体等待者已满 | 429 | `TOKEN_CONCURRENCY_LIMIT` | 1 |
| 全局等待者已满 | 503 | `SERVER_BUSY` | 1 |

`Retry-After: 1` 表示至少等待一秒后再尝试，不保证一秒后一定有名额。错误计数按原因统计，不能把这一类拒绝计入“未知内部异常”。

### T2. 短请求在途限制与基线边界

主要修改：`auth.go`、`internal/store/token.go`、`external_v2_handlers.go`、`quick_create_handler.go`、`verification_service.go`、router 装配与 HTTP 请求体读取设置。

1. 受保护业务路由在查询数据库鉴权之前取得全局短阶段名额，鉴权成功后按稳定主体再取得主体名额。不能把保护只放在鉴权之后的 handler/service。按当前 router 列出出号、取码、操作查询及所有兼容别名的覆盖表，包括 API 组外的 `/mail/code` 别名；依据真实路由装配接线，不凭 URL 字符串猜测。
2. 出号、创建取码任务、即时查询和操作查询持有短阶段名额到业务处理结束。未知主体只计全局，不按攻击者提供的 Token 字符串建计数桶。
3. 长轮询初始鉴权、归属读取、订阅和订阅后的数据库复查在短阶段内完成。未决任务先取得等待者名额，真正挂起前释放全局/主体短阶段名额；挂起期间由等待者上限约束。
4. **禁止让一个 120 秒长轮询一直占着短请求池的名额**，否则 128 个等待请求就会挡住出号和任务创建。释放函数必须幂等，middleware 的最终 defer 不能重复扣减已释放计数。
5. 同一调用链只能取得一次同类名额。入口 middleware 持有该次 HTTP 短阶段名额时，service 不再重复获取。不同入口复用业务服务；后台调用遵循自身 Worker/上游预算，不能制造另一套 HTTP 计数。
6. 单主体短阶段超限返回 `429 TOKEN_CONCURRENCY_LIMIT`，全局超限返回 `503 SERVER_BUSY`，都附带 `Retry-After: 1`。挂起后的唤醒、最终 DB 复查及凭据复查由已接受等待者数量约束，不能声称入口的 128 上限覆盖全部 DB 调用。必须测同步唤醒和同时到期的峰值；没有测到问题前，不再增加一个完成队列或信号量。
7. 新增返回明确错误的 Context 版 Token 校验，使用 `QueryRowContext`。HTTP 鉴权、v2 长轮询的开始/交付复查、兼容取码交付复查统一调用它；原有无 Context 方法只有存在真实调用时才保留为同一实现的封装。无记录、撤销、过期继续返回既有 401；DB 故障返回明确服务端错误，例如 `503 AUTH_BACKEND_UNAVAILABLE`；Context 取消传回取消处理，不得伪装为无效凭据。保留 Token ID、scope、过期格式 fail-closed 和成功后非阻塞活跃时间更新。
8. 当前 1 MiB body limit 只限制大小，不限制读取时间。前置名额覆盖 JSON 读取时，必须给实际 Body.Read 有效的读取预算；优先验证 `http.Server.ReadTimeout` 的 30 秒候选值与现有 10 秒 ReadHeaderTimeout，或等效的可证明读取 deadline。仅派生一个超时 Context 不保证阻塞的 Body.Read 退出。用真实 TCP/实际启用的协议验证慢 JSON 读取释放名额、正常小 JSON 成功、120 秒 GET 长轮询仍正常；不增加会误杀长轮询的短 WriteTimeout。
9. 基线槽位沿用现有可取消机制。等待基线槽位的请求数量被外层短阶段限制，并有有限预算；若当前缺少建立基线阶段预算，使用 30 秒候选上限，覆盖 lease 锁、槽位和网络读取。
10. 已经观察到取消时，不启动后续基线网络操作或新事务，等待/SQL 使用 Context；不能保证取消与 Commit 竞争时事务一定没成功。若提交成功但响应丢失，保留真实任务，带键请求按 T11 找回；无键请求仍可能返回 409，不能虚构它已有恢复办法。
11. 健康探针不占业务名额。现有 admin-only 统计保留独立且有界的观察通路，不能绕过鉴权或开放排障接口；业务满载时仍应能查到容量和拒绝原因。
12. 明确服务端阶段期限：鉴权查询、GET 初始纯 DB 阶段及结果交付的 DB/凭据复查，分别使用不超过请求剩余期限的 5 秒候选预算，包含 sql.DB 连接池等待。客户端不主动断开时也必须退出。建立基线沿用前述 30 秒候选预算；现场出号/登录等真实上游操作保留其业务预算与未知结果恢复规则，不机械套 5 秒。短阶段 Context 仅传给该阶段的锁/查询，不能作为后续 30/120 秒长轮询的父 Context；等待仍使用原请求与服务停机生命周期。内部 DB 阶段到期是可定位的服务端超时，不是凭据失效，也不是正常 pending/VERIFY_TIMEOUT；父请求已取消则停止响应。

本阶段限制的是并发占用。短请求 QPS 限制解决另一类问题；只有测到高频短轮询/拒绝请求消耗 CPU，才新增按稳定主体的令牌桶，不先堆叠所有层级的 QPS/IP 规则。

### T3. IMAP/HME 活跃操作硬限制

主要修改：`internal/mail/pool.go`、`internal/account/hme_pool.go`、`client_factory.go`、Manager 装配和后端错误映射。

1. 保留同一个 IMAP 池键、同一个 HME 账号的既有串行保证，不放宽 go-imap 的使用并发。
2. 完成账号级序列化之后、实际建立连接或执行网络操作之前，获得全局活跃操作名额。等待同一母号的请求不能先长期占满全局上游名额。
3. 活跃操作准入满时显式返回可识别的忙错误，不继续连接网络或执行业务。HTTP 入口映射为 `503 UPSTREAM_BUSY` 与 `Retry-After: 1`；后台 Worker 结束该次尝试并保留任务、扫描位置，后续正常同步再处理。
4. 准入满不能误标为 Cookie 失效、账号封禁、无库存或业务成功，不能触发额外重登录、直连 fallback 或无界 retry。
5. 名额覆盖冷连接、连接健康检查和实际业务执行，在错误和取消时释放；取消网络请求沿用已有真实 TCP/HTTP 中断逻辑。
6. 核对池外的直接客户端路径：`manager_validate.go`、`client_factory.go`、邮箱绑定检查和 WebMail 读取。不要只改一个池就称“所有网络调用已全局受控”；属于同一资源预算的绕行路径必须接入，独立登录链路的预算在报告中明确说明。
7. 明确计量单位。HME 上限若统计一次客户端借用/业务操作，就不能把它当作 TCP socket 上限；借用内已有的有界 HTTP 批处理扇出需要记录实际峰值，禁止新增无界内部并发。
8. 不持有连接池全局 map 锁执行网络 I/O；不在信号量满时持该锁等待；锁顺序应写入注释并由并发测试验证。
9. IMAP 采用共享硬总量及后台保留容量，按第 5 节从同步并发派生。工作类别由内部调用方明确传递，不能由 HTTP 参数/Header 伪装。取得全局操作名额仍在账号级串行锁之后；缓存借用阶段同时满足 T6 的后台保留规则，不能只保留操作槽位却让前台 pin 占满所有池条目。
10. 持续前台基线/管理流量与后台已有任务的混合测试，必须证明后台持续进展。保留容量解决全局资源抢占，不保证 Apple 响应时间或同母号排队公平；若热点账号仍因前台队列造成后台持续超时，需在同一个账号借用机制内解决公平性，不开第二实例绕过串行锁。HME 是否需要类似后台保留，按真实后台调用链判断，不把 IMAP 的同步并发机械套给 HME。
11. `backend_mail.go` 的 `GetMailboxBoundaryContext`、`ListInboxContext` 及相关邮件读取适配层优先识别池忙/上游忙错误，再进入已有错误包装或 WebMail fallback；不得把忙包装成 502、CAPABILITY_UNSUPPORTED 或 Cookie 失效。HME 创建/验证错误适配也必须保留可识别的忙原因。
12. 全局与前台活跃计数在一次原子准入中更新：例如 IMAP 总量 32、保留 5 时，必须同时满足总数小于 32、前台请求时前台数小于 27。先各自读取计数再增加不能防止超额；若采用两个非阻塞槽位，实现失败回滚和恰好一次释放，不持已取得的槽位排队等待另一个。等待账号锁的引用不算正在执行的网络操作，统计不能混淆。

本阶段先得到“活跃操作不会无界增加”的保证。缓存池最大条目数、全部闲置连接数的硬边界由 T6 完成，不能用活跃操作上限代替缓存容量验证。

## 7. 数据库、邮件同步和缓存任务（安全项优先，性能项按证据实施）

### T4. Store 锁等待可取消，准入预检只读

主要修改：`internal/store/store.go`、`inventory_claim.go`、`inventory_vreq.go` 以及使用该锁的热路径。

1. 先梳理 `Store.mu` 的所有调用，确认其真实职责和锁顺序。
2. 对仍需共享业务写锁的 Context 热路径，使用一个支持 `LockContext(ctx)` 的互斥原语；非 Context 方法的 `Lock()/Unlock()` 使用同一个底层原语，不添加第二把 semaphore 后继续等原来的不可取消 mutex。明确零值/构造初始化规则，不能使未初始化 channel 永久阻塞。保留原有互斥边界和锁顺序，不借此重构全部 Store API。
3. `ClaimInventoryAlias`、任务创建准入/原子插入、批量任务完成/失效等 Context 方法在等待锁时可退出。已经取消的 Context 即使碰巧取得名额，也必须释放并退出，不执行后续业务写入。
4. 不为锁增加 goroutine 代等，不能采用“外层返回取消、后台仍执行写入”的假取消。
5. `CheckVerificationRequestAdmission` 移除过期 UPDATE，使用有效期条件做只读预检。预检不持有/等待全局业务写锁；可用一条汇总 SQL 获得同 lease、主体、全局计数，或使用有限的只读查询。预检是建议性拒绝，最终插入事务必须重新仲裁 lease 冲突、配额并处理过期占位。过期状态变化和并发创建不能依赖预检快照保证正确；实际事务传播每个真实 SQL 错误。
6. SQLite 事务/CAS/唯一约束继续是正确性边界。可取消的 Go 锁不能替代数据库约束。
7. 保留 WAL、DSN 级 busy_timeout、连接池数量；先测量，不通过把 SQLite 连接数从 10 增到几百来掩盖单写入限制。
8. 补齐范围内权威持久化的错误传播。当前 `CompleteMatchingVerificationRequests` 对 request_id 的 Scan 失败会继续，未检查 rows.Err，更新后的结果读取失败也被忽略。改为遇真实错误立即返回并回滚，不返回部分集合加 nil 错误；读取零条且无错误才是合法零匹配。Worker 只有在权威事务成功后才发布/标记指纹/推进 checkpoint；SQL故障、取消和结构损坏不能被“未匹配到任务”掩盖。故障注入覆盖行迭代和更新后回读失败。

### T5. MailSync 批量基线查询与批量代际失效

主要修改：`mail_sync.go`、`inventory_vreq.go`、schema/迁移及相关回归测试。

1. 新增按邮箱集合查询的 Store 方法，一次查询返回每个邮箱的基线统计。大量参数分块处理，建议每块不超过 500 个邮箱。
2. 替换 `fetchAndPublishBatchResult` 及 `scanAndPublishPages` 中逐邮箱 `GetMinBaselineUIDByEmail` 的循环。
3. 保留现有判定：有活跃任务但不是全部具有有效 IMAP 基线时，不能只取 `MIN(baseline_uid)` 就假装严格任务有效。批量结果要包含/表达任务总数、有效基线数、最小 UID；过期、provider、mailbox/代际规则保持。
4. 获取当前 UIDVALIDITY 后，按邮箱集合批量失效不匹配任务，再批量重读仍有效基线。不能省略代际检查，也不能复用检查前的过时状态。
5. 批量查询失败显式报告；不得把失败当成“没有严格任务”然后降级读历史验证码。
6. 继续从“内存订阅者 UNION 数据库活跃任务”获得扫描需求。没有 HTTP 等待者的持久化任务仍必须收信、完成，并能在重启后恢复。
7. 当前按母号批量扫描和正文批量读取保持正确性；同一别名多个等待者不会制造等倍上游拉信，但不同母号共用同一 Gmail 时仍会分别扫描同一收件箱。共享物理邮箱的聚合读取按第 10.3.1 节先测量、再决定实施，不把连接池复用误报为扫描已合并。
8. 记录单轮数据库调用次数、涉及 alias 数、母号数和同步耗时，验证减少的是 N+1 调用，而不只是移动循环位置。
9. 扫描需求来源的正确性保护不等待批量性能改造。`ListActiveVerificationWatches` 出错时，记录失败原因和聚合计数，结束本轮并保留任务/checkpoint；不能当成零任务空闲，也不能只扫描订阅者就报告本轮完整成功。服务正常停机取消单独处理，避免错误日志刷屏；后续由既有 ticker/Trigger 重试，不再创建重试 goroutine。
10. 重启场景记录逐 alias 路由点查数量。当前 `resolveAccountFromStore` 调用的 FindAliasRoute/FindLeaseAccount 使用 bool，需在被本轮触及的恢复扫描路径中传播真实 DB 错误和 Context，不能把查询失败送入未知母号盲探。若基准显示冷启动路由 N+1 成为瓶颈，再做批量解析，保持既有路由优先级、授权和账号归属，不新建一套库存/路由真相源。

候选索引按真实 SQL 的 `EXPLAIN QUERY PLAN` 和写入成本选择，通常围绕 `(alias_email, status, expires_at)`、`(principal_kind, principal_id, status, expires_at)`、`(lease_id, status, expires_at)`、全局 `(status, expires_at)`。不能四个一律添加后不验证；若 SQL 使用 `LOWER(TRIM(alias_email))`，普通邮箱索引不一定能命中，需保持查询与规范化/表达式索引一致。

新增索引遵循现有幂等 schema/迁移机制，验证新库、旧版本副本、重复启动和失败回滚。不在生产数据库手工执行临时 ALTER/DDL。

### T6. 池容量与借用/驱逐生命周期

主要修改：`pool.go`、`hme_pool.go` 及池的并发测试。

1. 保留默认 IMAP 缓存 50、HME 客户端缓存 200，先获得真正的容量边界，不直接按邮箱数扩大缓存。
2. 新条目创建时，若已达到容量且没有可安全驱逐条目，返回明确池忙错误；不要在“都忙”时突破容量。
3. 对借出到释放全过程进行引用/pin 管理。当前“拿到条目指针”和“取得账号锁”分离，需要回归复现：期间能否被驱逐并为同一账号创建第二个条目。未复现前报告为待验证竞态，修复后用确定性屏障证明同键只有一个受控实例。
4. 正在使用或排队引用的条目不能被当作空闲条目驱逐。取消等待者要释放引用，驱逐、账号删除、凭据更新和 Close 要协调。
5. 不在关闭或驱逐期间泄漏已脱离 map 的客户端；关闭后拒绝新借用，不能关闭一半又创建新池条目。
6. 明确锁顺序：map 锁只保护注册、引用计数和生命周期标记，不持它等待账号锁或关闭网络。正常路径在 map 锁内取得条目并 pin，释放 map 锁后等待账号锁；结束时先释放活跃操作名额和账号锁，再归还 pin。Close 先在 map 锁内标记整个池 closed 并登记/摘出待关闭条目，释放 map 锁后等待引用退出并关闭客户端。当前 IMAP Close 持 `p.mu` 等 `pc.sem`，必须一起修改，否则新增的归还 pin 逻辑可能产生 ABBA 死锁。
7. 账号 drop/凭据切换期间，同键旧实例未退出前，不能提前删除注册键并允许新实例同时运行。用现有条目生命周期协调等待与销毁，保证旧凭据不复用；不靠 Close 的 TryLock 失败后跳过忙条目来结束清理。关闭必须可再次等待最终结果。
8. IMAP 池为 MailSync 保留可借用的条目容量：在当前 50 条硬容量、同步并发 5 下，前台借用及尚未关闭的条目合计最多占 45 个不同条目，后台可使用保留的 5 个；多个前台引用同一条目不重复计条目容量。同步并发 16 时相应前台边界为 34。闲置条目可安全驱逐，不能仅按 map 总长度拒绝后台。该计数与操作活跃数是不同边界，测试前台等待者 pin 饱和但后台仍能借用不同母号。
9. 驱逐或关闭过程中尚未完成断开的连接也属于资源占用，不能靠先删 map、无限补新条目突破真实连接边界。明确 closing 条目计数/释放时机，不增加没有必要的连接补偿队列。
10. 区分 `cached_entries`、`borrowed_entries`、`closing_entries`、`open_connections`、`active_operations`；HME 一个客户端可能有多个底层连接，不能声称 200 个条目就等于最多 200 个 socket。
11. 用上游建连计数和进程文件描述符验证容量保护，不只断言 map 的长度。必须覆盖“持账号锁准备归还 pin，同时 Close 开始”的确定性交错，证明无需测试超时碰运气判断死锁。
12. 同一 IMAP 条目可能同时有前台和 MailSync 引用。map 锁内原子维护条目引用及类别计数：总占用按不同条目的并集计算，前台占用按有前台引用/尚未释放前台资源的不同条目计算；共享条目不算两份总容量。取消、交付、drop、驱逐和关闭都更新同一真相源，不为预留数另建可能漂移的注册表。

### T7. EventBus 周期清理与安全去重

主要修改：`internal/mail/eventbus.go`、Server 生命周期及 EventBus 测试。

1. 接入每分钟清理一次的可停止周期任务。不能放在可能持续很久的单轮同步之后，导致大规模同步时清理一直得不到执行机会。
2. 删除已过期事件及空邮箱 bucket；消费、读取、订阅剪枝等路径也应移除空 bucket，不累积历史邮箱空键。
3. 同一规范化邮箱、同一完整事件身份的重复缓存只保留一份；EventID 必须非空且身份含 provider/account/mailbox/UIDVALIDITY/UID 或相应 WebMail 身份。空或弱身份不凭 code/时间去重。保留原始过期时间和既有顺序，不通过重复发布无限延长 TTL。
4. 本轮保留所有未过期、尚未被既有流程消费的事件。撤回初版“每邮箱 64、全局 65536”和“满后拒存新事件”的建议，不能通过淘汰旧事件或静默丢新事件达到容量目标。
5. 缓存去重与通知是不同责任：不能因为缓存里已经存在同一身份就跳过业务仍需要的唤醒。保留 Worker 的邮件指纹去重，避免把已用历史码重新广播给 fresh 查询；核对直接 Publish 入口，明确其通知语义。
6. 严格 v2 仍先持久化再发布，数据库失败不推进未完成 checkpoint。兼容查询缺少同等持久结果恢复，`markPublished` 又可能阻止再次广播，因此“无人订阅时缓存拒存，之后查询回源”在当前实现不是完整方案。
7. 测试既有 fresh、最早匹配缓存顺序、基线过滤及单事件消费行为。发布时无人订阅、之后在 TTL 内订阅仍能取到原结果；相同邮箱密集发布不同事件不能漏掉未消费结果。
8. 若压测证实未过期事件内存超过预算，另立后续任务，先实现可恢复的结果保留/回源机制及明确过载契约，再考虑硬容量。不自动引入 Redis 或另一个邮件服务；未完成这个闭环前只能报告“已清理过期/空键并减少重复”，不能报告缓存完全有界。
9. 清理协程随 Server 关闭并被等待；测试重复启动/停止，不产生泄漏。记录缓存数量、清理/去重次数和清理持锁耗时，验证周期全表清理不会在目标数据量下阻塞正常发布。

## 8. 关闭、监控与网络恢复契约

### T9. 优雅停机与反向代理

1. 将 HTTP 等待请求的关闭信号与后台清理生命周期分开。开始停机先拒绝新业务、取消长轮询，HTTP Shutdown 使用自己的有限预算；后台 Stop/等待用独立预算。
2. HTTP 关闭预算耗尽不代表 Worker 已结束。继续沿用当前 CloseContext 的“清理只启动一次，调用方超时后清理仍继续，后来者可再次等待”保证。
3. 所有 Worker、缓存清理任务和正在使用客户端的请求退出后，依次关闭客户端池、Store。不能把一个已超时的 shutdownCtx 传下去后立即关闭数据库。
4. 请求 Context 取消是取消，不能统一包装为 `500 INTERNAL_ERROR`；客户端断开不继续写响应。v2 自身等待计时器到期仍返回 pending，不能与网络/数据库 deadline 混淆。
5. timeout 秒数在转换 `time.Duration` 之前截到既有上限 120，避免超大合法整数乘秒溢出；不要借此改动全部既有非法参数的兼容行为。
6. 修正 Nginx/Caddy 验证码 matcher，覆盖 v2 `/api/external/v2/verification-requests/*` 与实际兼容取码路径；超时按应用最长等待加余量设置，已有 130 秒可作为初始值。
7. 真正部署若经过 CDN/其他网关，以整条链路最短超时为准。客户端通常使用 `timeout=30`，HTTP 客户端预算 40 秒；不把默认客户端等待强行改成 120 秒。
8. 对 Nginx 说明 worker_connections 同时计入客户端及到 Go 的连接；同一个请求经代理可能占两条连接。核对 HTTP/2 stream、nofile、容器和代理容量，不能只调整其中一个数字。
9. Compose 主服务的 stop_grace_period 应覆盖已验证的关闭预算，例如先测 30 秒；保留主服务与 Camoufox 各自资源预算，不能用整机空闲内存推断主服务可用容量。
10. 主要修改必须包含 `Server.Run` 与 `main.go`。当前 Run 停机超时返回 error 后，main 的 log.Fatal 会立即 os.Exit，跳过 defer 并终止清理协程；不能把进程内 CloseContext 测试当成真实 SIGTERM 完整退出证据。正常停机先拒绝新业务/取消等待和 Worker，再由一个明确的协调流程等待请求退出及资源清理；HTTP drain 到期时显式关闭剩余连接并等待 handler 退出，不能立即关 DB。Run 的返回点、main 错误处理及重复 Close 不得绕过这个流程。
11. 定义硬总预算与结束条件。若 HTTP drain 与后台清理串行，Compose 的 stop_grace_period 必须大于两段预算之和再加余量；若并行则按实际关键路径验证，不机械写 30 秒。清理在总预算内完成才报告优雅退出；总预算耗尽只能报告未完成范围并按既定退出策略结束，不能承诺退出后的 goroutine 还会继续执行。用独立子进程收到 SIGTERM 的测试验证生命周期，并在可用环境验证容器 stop。

### T10. 增加现有管理统计，不新增公开排障服务

在已有 admin-only `/api/system/stats` 增加一组聚合统计；保持现有字段，通过标准库计数器实现，不引入监控 SDK。

必需统计：

- 实际生效的任务/等待者/短请求/上游容量配置。
- 活跃任务总数、全局等待者当前数及峰值、短请求在途数及峰值。
- 准入拒绝次数，区分单键、主体、全局、基线/上游/池容量。
- IMAP/HME 活跃逻辑操作、池条目、借用/关闭条目及前台/后台占用；无法准确计量的 socket 数明确省略，由 OS 压测采集。
- `sql.DB.Stats()` 的连接数、InUse、WaitCount、WaitDuration；这与 Go 业务锁等待是不同指标。
- Store 热路径锁等待/事务耗时的聚合记录；先用计数、总耗时、最大值，p95/p99 由压测脚本计算。
- 单轮 MailSync 的母号/邮箱数、耗时、数据库调用量、失败分类。
- EventBus 订阅总数、缓存邮箱/事件数、清理数、去重数及清理耗时；本轮不实现静默容量淘汰/拒收。

不能把 request_id、邮箱、Token 原文当成无限标签或公开统计维度。日志不记录密码、Cookie、Authorization、验证码或完整邮件正文。不得把数据库统计失败显示成确定的 0；可标记不可用/错误。

长期数据清理只做评估和增长统计：不要自动删除 operations 幂等记录、分配凭据或重启恢复所需的记录。当前 lease 清理有安全暂停，不在本轮擅自恢复。未来删除终态任务必须先定义历史查询/幂等保留契约，完成依赖审计和独立验收。

### T11. 同一 v2 POST 的可选任务创建幂等重放

这是创建任务的网络恢复契约补齐，不是提高并发数字。当前代码只有按 request_id 查询；创建成功后响应丢失，客户端不知道 ID，重试 409 也不返回它。仅在 409 附活跃任务 ID 仍不能覆盖原任务已经终态的情况。

主要修改：`external_v2_handlers.go`、`verification_service.go`、`inventory_vreq.go`、schema/迁移、`API.md` 与客户端示例。复用同一业务服务和持久化任务，不新增 v3、第二套取码流程或通用操作框架。

1. 现有 `POST /api/external/v2/verification-requests` 支持可选 `Idempotency-Key`。不带键保持当前创建及同 lease 活跃冲突 409；带键按 `(principal_kind, principal_id, key)` 隔离。同一分配和取码创建使用各自的业务意图键，不能隐式复用出号 operation 作为任务。
2. 按实际生效参数生成有版本的规范指纹：将 email/lease_id 按现有规则解析为授权的实际 lease，记录 lease_id 与固定 mailbox=INBOX 等真正影响任务的输入，规范结构序列化后哈希。等价 email/lease 表达应得到相同指纹；不要把服务生成的基线、时间或 request_id 放进指纹。键去首尾空格后不能为空、最多 128 字节，拒绝控制字符，校验失败为 400，不把键原文放进无限日志/指标维度。
3. 简单持久化方案：在现有 verification_requests 增加创建键和指纹字段，历史行为空；对非空创建键增加主体+键唯一索引。字段/索引 DDL 在启动时的 schema 迁移事务中完成，按项目流程更新版本/校验；运行时创建事务只原子提交任务行及其中的键、指纹，不做 DDL，也不创建另一个职责重复的内存真相源。验证历史库、迁移中断、重复启动，以及所有读取/CAS 更新保留新字段。
4. 重放仍检查当前凭据、scope 和资源归属。相同主体/键/指纹返回原 request_id、原基线和原 expires_at，不新建任务、不重读基线、不延长有效期；不同指纹返回 `409 IDEMPOTENCY_CONFLICT`。不同主体同键不能互相查询或冲突。
5. 查重先于活跃任务配额与同 lease 活跃冲突判断，已有任务即使配额满或已经 succeeded/expired/invalidated，也能找回。不能只按 active 状态查重。不同键对同一 lease 的并发创建仍遵守一个活跃任务与既有 409。
6. 复用当前可取消键锁原语：带键时先取得独立命名空间的主体+创建键锁，再按既有流程取得 lease 锁，固定顺序，锁内重查持久记录；不带键只用既有 lease 锁。原子事务再次仲裁唯一键、指纹、lease 和配额，不能只依赖内存锁。这样同键响应丢失后的并发重试不会重复读取基线，同键不同 lease 也不会各自先打一次 IMAP。等待数量受 T2 约束，锁归零即回收。
7. 创建响应保留现有字段。重放携带原 request_id 和当前真实 status；`baseline_ready` 仅对持久状态 ready 且未过期的任务为 true，终态/失效/已过期为 false。必要的过期 CAS 不能覆盖已成功终态。客户端遇 succeeded 读取原结果，遇 expired/invalidated 处理原意图失败；需要重新发送验证码时显式创建新业务意图与新键，不能由重试代码自动换键。基线代际是否仍有效由既有扫描/失效规则判定，不在重放时另读上游。
8. 基线失败或取消且任务确实未提交时，可用同键再次尝试；提交结果不明确时必须先按同键查持久记录。提交成功后的网络响应丢失不撤销任务。带键重放返回 200，仍使用同一创建响应结构；不把所有无键 409 也改成成功。
9. 本轮不删除或在到期时清空创建键/指纹。取码任务有效期与幂等保留期限是两个概念；本轮沿用任务记录保留，增长纳入统计，后续清理先定义重试窗口和历史查询契约。

验收必须覆盖：并发同键只有一次基线和同一个任务；同键不同参数 409；不同主体隔离；提交后模拟响应丢失，再分别在 active/succeeded/expired/invalidated 状态重试；配额满后的重放；重启与旧库迁移；无键请求契约未改变。T11 未交付时明确报告 POST 网络丢响应恢复仍有限，不能宣布完整客户端重试闭环已经实现。

## 9. 业务回归测试与检查

使用真实 router/handler、临时 SQLite 和可控假上游，测试关注行为边界。采用 channel/barrier 控制时序，避免固定 sleep 碰运气。

| A12 | 批量基线含过期、无效 provider、代际变化与 SQL 故障 | 与原严格语义一致；错误不降级为旧码读取 |

## 10. 可重复的压力测试与容量验收

### 10.1 压测环境

- 假 Apple/IMAP 或现有 fake backend，使用临时数据库与唯一的合成邮箱；不能访问生产数据库或消耗真实 Apple 建号配额。
- 分别运行“真实 handler + SQLite + fake backend”和“隔离 IMAP/HTTP 测试服务 + 真实客户端池”。前者测业务逻辑，后者测网络/连接生命周期；两者不能互相代替。
- 记录 SHA、OS、CPU、内存、Go 版本、容器限制、所有生效配置、连接协议、数据量和假上游延迟。优化前后必须同条件。
- 有条件时压测客户端与被测服务分开运行，并验证客户端自身没有成为连接/CPU瓶颈。
- 新脚本优先复用已有基准/测试支撑，使用 Go 标准库即可，不为跑压测安装一整套平台。

启动 2000 个等待者前必须先准备 2000 个有效任务。不能用缺省 50 个任务的 Token、或查询不存在的 request_id，得到一堆快速 404/429 后声称完成 2000 长轮询压测。

正常容量验收按入口短阶段容量逐批建立长轮询，使用有界建连并发、Retry-After 和抖动，等待实际挂起数达到目标后再开始测稳态。一次同时发起 2000 个 GET 可能触发 128/64 的入口边界，即使长期等待者还有余量；这种突发拒绝单独统计，不能与“2000 条已建立连接持续运行”混淆。必须保留实际接受数、重试数和建连耗时，不只报发起数。

请求数与到达速率也要分别记录：2000 条保持连接与每秒新建 2000 个任务是两个目标。一次性突发允许显式拒绝；正常负载验收使用有界客户端和明确的持续到达速率。

### 10.3 母号与物理邮箱分布决定同步时延

单轮粗略估算：

```text
一轮同步时间 ≈ 活跃母号数 / 有效并行度 × 每母号实际处理耗时
有效并行度受 Worker 并发、上游操作预算、不同 IMAP 池键数量共同约束
```

例如 2000 个母号使用独立收件邮箱、有效并行度 5、每母号实际处理平均 0.5 秒时，仅这一部分约 200 秒；每个都用满 8 秒预算时，按这个模型约 3200 秒。尚未计算所有分页、正文、数据库、等待和连接重建，不能当作实测或严格上界。任务当前有效期 10 分钟，这类负载下任务可能未轮到扫描就已到期。poll interval=1 秒或 2 秒都不会让整轮变短。

当前 `WithMailClientContext` 对外部收件邮箱使用 mailbox.Email/IMAPHost/IMAPPort 取得池条目，`poolKey` 没有按母号 ID 分开，因此多个母号绑定同一 QQ/Gmail 收件邮箱时共用串行条目。若 2000 个母号都使用同一池键、每次实际读信 0.5 秒，则这个简化模型的有效并行度是 1，约需 1000 秒；调高同步并发只会增加等待同一锁的调用。该模型用于说明约束，不代表真实邮箱已测得 0.5 秒。压测分别报告母号数、实际池键数、网络执行时间与锁等待；不能把含锁等待的耗时再重复加进公式。

因此报告要明确：2000 个 HTTP 等待请求稳定存活，不等于 2000 个母号上的验证码都能在 30 秒内返回。若“2000 个母号都要低延迟”是实际负载，应在上游容量允许范围内测同步并发 16 等候选值；仍达不到时据实报告吞吐/时延边界，而不是不断抬高所有并发。

当前 loop 在 syncOnce 返回前不处理新 Trigger，单账号 8 秒预算也不覆盖等待账号槽位的时间。测量整轮耗时、新任务首次扫描等待和按母号的进展，不能只报快账号的平均耗时。若真实工作负载要求整轮期间也能及时纳入新任务，需要另一个明确改动组完成有轮次预算、持续轮转/可恢复扫描的公平调度；先保留既有 checkpoint 与取消语义，不用每个 alias 一个 goroutine 或加长任务有效期掩盖调度瓶颈。2000 别名集中在少量母号时，不预先强制重写调度器。

### 10.3.1 实际工作负载：多个母号共用一个 Gmail

用户已确认多个 iCloud 母号共用同一个 Gmail 收件邮箱；未提供母号数量、同时活跃任务数或真实邮件流量。此拓扑作为主要容量验收场景，不能假定 2000 个任务对应 2000 个母号或独立 Gmail，也不能把 Gmail 收件地址当成每任务等待者的分桶键。HTTP 等待仍按 request_id/别名/主体及全局限制。

本次静态核对确认：`WithMailClientContext` 按外部邮箱配置借用 IMAP，池按收件邮箱、服务器和端口复用串行条目；MailSync 的 `accountQueries` 和 checkpoint 仍按母号划分。同一连接复用不等于同一收件箱只扫描一次。池还会在密码或生效代理变化时关闭并重建连接；若共用 Gmail 的母号配置不同代理/授权码且没有统一生效配置，交替访问可能增加连接重建。当前用户是否存在这一配置差异未知，不能据此断言已发生重连风暴。

实施与验收要求：

1. 先用假上游复现多母号共享一个物理收件箱，固定活跃任务数和邮件流量，改变母号分布。分别计量邮箱边界查询、UID 页扫描、正文读取、连接重建、池等待、创建速率和收码时延。真实 Gmail 投递/限流单独验证，不自动发送真实邮件。原方案中已选的可靠性保护仍按原顺序完成，T5 的错误传播不等待此性能改造。
2. 若母号数增加造成重复网络读取或影响目标时延，性能阶段优先将共享收件箱的活跃别名聚合，复用一次增量扫描和批量正文读取，再按原始收件人匹配分发；先于盲目调大 Worker 并发。以既有池身份为基础验证生效连接配置一致，不能仅凭相同 Gmail 地址合并不同服务器、凭据或网络策略，不擅自关闭用户代理。
3. 聚合只复用已验证的物理邮件读取结果。lease、Token 权限、别名归属、对外交付的 account_id 和 MessageRef 仍按该别名真实母号生成并验证；不能把用于网络读取的某个母号身份写到其他母号结果中。保留每任务的基线、UIDVALIDITY、分页/checkpoint、先持久化后发布、故障后不推进游标、新任务加入及重启恢复保证。实际 Gmail 邮件必须保留可匹配的原始别名收件人信息，匹配不到时显式报告，不能靠模糊匹配猜归属。
4. 创建任务仍需取得该请求有效的邮件基线；共享扫描优化不会自动消除 POST 的串行基线读取。不能直接拿上一次扫描的 UIDNEXT 或使用任意 TTL 缓存代替新任务基线，否则可能把旧邮件交付给新任务。若另做并发基线合并，必须单独证明请求与边界读取的时序、任务创建后再发送邮件的契约及取消/代际语义。
5. A25 与主压测同时覆盖跨母号错投、同一物理 UID 对应不同账号引用、转发头缺失、读取/落库失败、新任务加入、解绑/换绑及重启。报告扫描合并是否实施、优化前后网络调用次数与收码时延，以及共享 Gmail 的已验证稳定档位；不能仅凭连接数少宣布可承载 2000 个任务。

### 10.4 连接数、到达速率和任务建立速度分别验收

以下只做容量模型，不是当前性能测试结果：

- 2000 个任务在无结果时每 30 秒重建一次长轮询，平均约 67 次 GET/秒；每 120 秒约 17 次/秒。实际需考虑处理时间、随机抖动和任务完成率，另测同一时刻重连的突发。
- 按当前普通 Token 的 30 秒 pending 路径，一次 GET 通常包含入口鉴权、服务开始凭据复查、任务初读、订阅后复查、等待结束复查、交付凭据复查，约 6 次 DB 读取；67 次/秒约对应 400 次读取/秒，另加 Worker 查询和新任务写入。不能把 2000 条等待连接理解成没有数据库负载，改造后按真实查询数重新计量。
- 基线并发 8、每次网络实际处理 0.5 秒且池键独立时，仅网络这一项理论上限约 16 个新任务/秒，建立 2000 个至少约 125 秒；共享单个串行邮箱时约 2 个/秒、至少约 1000 秒。还未算同步争用及 DB 等待；实际速率只能更低或通过有证据的业务改造改善。
- 当前任务有效期从完成基线后算 10 分钟，不能在真实慢上游中顺序建立到第 2000 个时，忽略前面的任务已经到期。准备负载必须再次核验活跃有效任务数；假上游可缩短其延迟以验证连接/逻辑容量，真实目标还须单独通过任务建立速度与邮件完成时延验收。

入口的 128、等待者的 4096、上游的 32 分别限制不同阶段；它们不是整个进程的 goroutine/连接数上限。登录、其他管理路由、net/http 接入以及后台工作的实际资源一并采集；不以某个准入计数代替 RSS/FD/连接与 DB 等待观测。

### 10.5 验收规则

正确性硬门槛：

1. 重复分配、串号、越权读码、错误基线取码、终态被覆盖均为 0。
2. 已实施保护层的峰值不超过其生效上限；所有容量拒绝可识别，没有无界等待。EventBus 本轮只有 TTL/去重治理，未过期事件无硬容量，单独报告内存规模；不得将其写成已满足硬上限。
3. 正常容量内的确定性假上游测试，允许完成的任务结果全部正确；不能把预期拒绝计入业务成功。
4. 取消、超时、重启后资源最终回到基线范围，计数 map/订阅不积累。RSS 不必立刻下降，结合 heap 与 FD 判断泄漏。
5. 正常负载无意外 5xx、panic、SQLite 锁死或长时间服务失去响应。
6. 过载时快速返回 429/503，降载后能恢复；不依赖重启释放资源。
7. 容量内混合负载的后台任务持续进展；客户端创建请求丢响应后，带键重放能恢复 active 和终态任务。只证明 HTTP 连接存活不能替代这两项业务验收。

性能验收：分别报告 allocate、create-vreq、即时 GET 的处理 p50/p95/p99，报告长轮询的“事件持久化/发布到 HTTP 返回”延迟。不要把正常等邮件的 30 秒算成 API 运算耗时，也不要把快速拒绝混进成功请求延迟让曲线变漂亮。

可先使用以下待验证预算：本机隔离假上游下，池出号 p95 小于 500ms、p99 小于 1s；过载拒绝 p95 小于 200ms；进程内已发布事件到等待者返回 p95 小于 500ms。它们是验收目标而非现有测量，最终需报告硬件和 workload；真实端到端收码包含邮件投递与上游延迟，单独量测。

若 2000 任务候选配置未通过，交付“已验证稳定档位 + 失败指标 + 瓶颈”，保留安全配置，不把配置数字写成已实现容量。

## 11. 客户端接入要求

统一示例使用现有 v2：

1. 一次业务分配生成并持久保存一个 Idempotency-Key；分配网络超时或可重试忙状态后保持相同键/请求体。
2. 获得 lease 后，为一次取码意图另生成并持久保存创建 Idempotency-Key，再创建取码任务。仅在原任务仍 ready、未过期且 baseline_ready 时触发外部发送；重放若已 succeeded 则读取原结果，expired/invalidated 按原意图失败处理，不自动再次发送或换键。
3. 同一 request_id 同时只有一个长轮询，推荐 `timeout=30`、HTTP 客户端超时 40 秒。收到 pending 继续查同一个任务，不重新出号或创建另一个取码任务。
4. 429/可重试 503 读取 Retry-After，添加随机抖动；连续忙状态使用有上限的退避，受任务期限与业务截止时间约束。
5. `POOL_EMPTY` 沿用更长的 Retry-After；401/403 停止并处理凭据；404 检查 request_id/归属；409 检查幂等冲突或已有任务。不能统一无脑 retry 所有错误。
6. T11 交付后，创建 POST 网络超时保持同一创建键和参数重试，找回原 request_id。没有键或服务尚未实现 T11 时，现有 POST 丢响应后的 409 无完整恢复保证；明确报告并处理这个限制，不能为了绕过冲突换邮箱继续建任务。任务创建幂等不覆盖外部业务的“发送验证码”副作用，发送也需由调用方避免重复。
7. 用两个独立客户端并发池：短请求池控制出号/创建突发，等待请求池容纳已建立的任务。不能给所有 HTTP 请求共用一个小 semaphore，导致挂起请求阻塞下一批任务。

### 12.1 生产部署前提

- 完成全部正确性门槛，明确哪一个负载档位通过，不以“Go 支持高并发”替代证据。

### 12.2 回滚规则

1. 先降低/停止新业务流量，保留日志和当前数据；优先回滚到已经准备的上一版镜像，同时保留当前持久化数据和同一 Master Key。
2. 只有确认上一版能够读取当前 schema/凭据格式时，才能只换镜像。版本检查拒绝打开更高版本数据库时不能强行改 user_version。
3. 若 schema 不兼容，保存当前一致快照，使用已测试的兼容回滚代码或迁移方案保留新增分配/幂等记录。
4. **上线后已经接过新业务，禁止直接恢复上线前数据库快照**：这可能丢失已发放邮箱记录，导致再次发号。恢复旧快照仅适用于尚未接受新业务或已完成新业务数据保全的情况，并需单独授权。
5. 不删除 data，不重置 Master Key，不运行 `down -v` 作为修复步骤。
